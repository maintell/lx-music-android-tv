# 国际化体系（i18n）

> 读者获益：本文档说明语言包如何组织、运行时如何翻译、切换语言如何刷新整个 UI，以及新增一种语言需要动哪些文件。读完你新增 UI 文案时不会踩「硬编码中文」「key 命名不一致」「语言包没注册」的坑，也能给项目新增一门语言。

## 设计依据

本文档对应 [design-doc.md](../design-doc.md) 的以下内容：

- **6.3 国际化（src/lang）**：语言包为 `zh-cn.json`（fallback）、`zh-tw.json`、`en-us.json`；运行时 `createI18n` 生成 `global.i18n`，提供 `t(key, vals?)` / `getMessage` / `setLanguage`，组件侧通过 `useI18n` hook；新增语言需按 `src/lang/Readme.md` 的 locale 列表命名并在 `src/lang/index.ts` 注册；开发辅助为 `.vscode/i18n-ally-custom-framework.yml`。
- **7 扩展点设计**：新语言 = 新增语言包 + 注册（见 6.3）。
- **3.4.1 启动流程**：初始化管道中 `initI18n` 在 `initTheme` 之后执行。

> 说明：本文档与 `../architecture.md` 的分层一致——`src/lang/` 是语言包与运行时所在，`core/init/i18n.ts` 负责启动装配。

## 1. i18n 架构

```
语言包（src/lang/zh-cn.json / zh-tw.json / en-us.json，均为扁平 key）
   │  src/lang/index.ts：import + 组装 langs/langList/messages
   ▼
createI18n(locale)（src/lang/i18n.ts）→ 返回 I18n 实例，挂载 global.i18n
   │  提供 t / getMessage / setLanguage / fillMessage
   ├─ 组件侧：useI18n() hook → 返回 t(key, vals?) 翻译函数
   └─ 非组件侧：global.i18n.t(key) 直接调用
语言切换：core/common.setLanguage(locale)
   ├─ updateSetting({ 'common.langId': locale })   // 持久化
   ├─ global.state_event.languageChanged(locale)   // 事件通知（页面级监听）
   └─ applyLanguage(locale) → i18n.setLanguage → hookTools.update → 所有 useI18n 重渲染
```

### 1.1 术语速查

| 术语 | 含义 |
|------|------|
| `locale` | 语言标识，`ll_cc` 风格（`zh_cn` / `zh_tw` / `en_us`），与 `src/lang/Readme.md` 清单一致 |
| `langId` | 设置键 `common.langId` 的值（`I18n['locale'] \| null`），持久化于设置 |
| `fallback` | 缺 key 时的降级语言，固定为 `zh_cn` |
| `availableLocales` | 已注册语言列表（`Object.keys(messages)`），决定设备语言匹配范围 |
| `message(s)` | 当前语言的 key→文案映射 / 全部语言的映射表 |
| `S2T` | 简体转繁体，仅作用于歌词文本（`player.isS2t`），与 i18n 独立 |

## 2. 语言包结构

### 2.1 语言包清单（`src/lang/index.ts`）

| locale | 名称 | country | fallback | 文件 |
|--------|------|---------|----------|------|
| `zh_cn` | 简体中文 | cn | ✅ | `zh-cn.json` |
| `zh_tw` | 繁體中文 | cn | - | `zh-tw.json` |
| `en_us` | English | us | - | `en-us.json` |

- **`zh_cn` 是唯一 fallback**：`createI18n` 中 `fallbackLocale: 'zh_cn'`，`getMessage` 在当前语言缺 key 时自动回退到 zh-cn，再回退为空字符串。
- 三个语言包当前均约 519 行、key 数量一致（新语言必须保证 key 集合对齐，否则 `Message` 类型检查不通过）。
- `langList` 供设置页渲染语言选项（`Basic/Language.tsx`），`messages` 供运行时按 locale 查表。

### 2.2 key 的命名组织方式

所有 key 为**扁平字符串**，用分隔符表达层级：

- `__`（双下划线）：模块/语义层级分隔，如 `sync__list_mode_title`、`list_import_tip__setting`、`setting__other_dislike_list`。
- `_`（单下划线）：单词连接，如 `setting_basic_lang`、`play_detail_setting_lrc_align`。

抽查几个 key 的层级含义：

| key | 层级解读 | 值（zh-cn） |
|-----|----------|-------------|
| `setting_sync_enable` | 设置 → 同步 → 启用 | 启用同步 |
| `sync__list_mode_title` | 同步 → 列表模式 → 标题（带 `{name}` 占位符） | 选择与「{name}」的列表同步方式 |
| `setting_basic_lang` | 设置 → 基础 → 语言 | 语言 |
| `sync_status_disabled` | 同步 → 状态 → 未连接 | 未连接 |
| `deep_link__handle_error_tip` | 深链 → 处理错误提示 | （错误提示文案） |

> 组织惯例：业务模块前缀（`setting_` / `sync_` / `play_detail_` / `deep_link_` 等）+ 动作/对象；同一屏幕的文案尽量在 key 上相邻（`setting_sync_*` 集中），便于维护与 i18n-ally 的自动补全。

## 3. 运行时 API（`src/lang/i18n.ts`）

`I18n` 实例的公开接口（`global.i18n`）：

| API | 签名 | 行为 |
|-----|------|------|
| `t` | `t(key, vals?) => string` | 等价 `getMessage`，是组件侧主要入口 |
| `getMessage` | `getMessage(key, val?) => string` | 取当前语言消息；缺 key 回退 `zh_cn`；再缺返回 `''`；传 `val` 时做占位符填充 |
| `fillMessage` | `fillMessage(message, vals) => string` | 用 `vals` 逐项替换 `{key}` 占位符（正则全局替换，值转字符串） |
| `setLanguage` | `setLanguage(locale) => void` | 更新 `locale`/`message` 并调用 `hookTools.update(locale)` 通知所有挂载的 hook |
| 属性 | `locale` / `fallbackLocale` / `availableLocales` / `messages` / `message` | 当前语言、fallback（`zh_cn`）、可用语言列表、全部消息、当前语言消息 |

**占位符**：消息中 `{name}` 形式，如 `sync__list_mode_title = 选择与「{name}」的列表同步方式`，调用 `t('sync__list_mode_title', { name: serverName })` 完成替换。`fillMessage` 内部用 `new RegExp('{' + key + '}', 'g')` 全局替换，同名占位符出现多次也会全部替换。

**`t` 与 `getMessage` 的区别**：二者行为完全一致（`t` 只是 `getMessage` 的别名，见 `i18n.ts` 第 87-89 行）；约定上组件侧用 `t`、强调「翻译动作」，需要显式语义的场景（如工具函数内）也用 `getMessage` 亦可，无强制边界。

### 3.1 useI18n hook

```ts
const t = useI18n()
// 返回 useCallback((key, val?) => i18n?.getMessage(key, val) ?? '', [locale])
```

- 组件挂载时向 `hookTools` 注册（组件卸载时移除），`setLanguage` 触发后所有注册组件重渲染，`t` 引用随之更新。
- 非 React 环境（core 层、工具函数、事件回调）直接使用 `global.i18n.t(key)`。

### 3.2 非组件层使用示例（真实调用点）

| 位置 | 用法 |
|------|------|
| `src/core/player/player.ts` | `setStatusText(global.i18n.t('player__getting_url_delay_retry', { time }))` |
| `src/core/music/utils.ts` | `throw new Error(global.i18n.t('toggle_source_failed'))` |
| `src/utils/tools.ts` | 对话框按钮 `confirmButtonText = global.i18n.t('dialog_confirm')`；分享 `global.i18n.t('share_card_title_music', { name })` |
| `src/utils/index.ts` | 时间差格式化 `global.i18n.t('date_format_second', { num: differ })` |
| `src/store/list/hook.ts` | 内置列表名 `lists[0].name = global.i18n.t('list_name_default')` |
| `src/core/version.ts` | `toast(global.i18n.t('version_tip_unknown'))` |
| `src/core/init/deeplink/utils.js` | `global.i18n.t('deep_link__handle_error_tip', { message })` |
| `src/core/init/userApi/index.ts` | `global.i18n.t('user_api__init_failed_alert', { name: info.name })` |

> 注意：这些调用点必须发生在 `initI18n` 之后（`global.i18n` 已赋值）；核心层函数若可能在初始化前被调用，需保证调用时序。

### 3.3 类型系统（编译期保证）

`src/lang/index.ts` 导出的类型：

| 类型 | 推导 | 作用 |
|------|------|------|
| `Message` | `Record<keyof typeof zh_cn, string> \| Record<keyof typeof zh_tw, string> \| Record<keyof typeof en_us, string>` | 三语言包 key 集合互相约束——任何一个语言包缺 key，类型就不满足联合 |
| `Messages` | `Record<'zh_cn' \| 'zh_tw' \| 'en_us', Message>` | 由 `langs` 数组推导的 locale → 消息映射 |
| `Langs` | `keyof Messages` | 合法 locale 字面量联合（'zh_cn' \| 'zh_tw' \| 'en_us'） |

`t` / `getMessage` 的 key 参数类型为 `keyof Message`，因此**写错 key 或漏补语言包会在编译期报错**，这是项目对语言包完整性的主要防线。

> 实际编译时 `Message` 取的是三包 key 集合的并集，但 `Record<keyof typeof zh_cn, string>` 分支约束了「至少与 zh-cn 一致」，因此以 zh-cn 为基准即可。

### 3.4 fillMessage 边界行为

- 占位符替换用 `new RegExp('{' + key + '}', 'g')`：同名占位符全文替换；值统一 `String(val)` 转换（数字/布尔均可）。
- 若消息中没有对应占位符，替换静默无效果（不报错）。
- key 含正则特殊字符（如 `.`、`(`）时会按正则语义解析，理论上存在误匹配；约定占位符只用字母与下划线即可规避。
- 若 `val` 中某 key 在消息中不存在，该键值被忽略。

## 4. 语言切换流程

### 4.1 初始化（`src/core/init/i18n.ts`）

```
读取 setting['common.langId']（默认 null）
  ├─ 合法（在 availableLocales 中）→ 直接用
  ├─ 非法/未设置 → getDeviceLanguage() 取设备语言，匹配则用
  │      └─ 都不匹配 → 回退 'en_us'
  │           └─ updateSetting({ 'common.langId': lang }) 持久化
  └─ setLanguage(lang)（core/common 版）
global.i18n = createI18n()  // 默认 locale 为 'zh_cn'，随后 setLanguage 覆盖
```

### 4.2 用户切换（设置页 `Basic/Language.tsx`）

`Language.tsx` 用 `langList` 渲染语言选项，选中即调用 `core/common.setLanguage(id)`：

```ts
export const setLanguage = (locale) => {
  updateSetting({ 'common.langId': locale })       // 1. 持久化（configUpdated 广播）
  global.state_event.languageChanged(locale)        // 2. 事件总线通知
  requestAnimationFrame(() => { applyLanguage(locale) })  // 3. 下一帧切换运行时
}
```

- `applyLanguage` = `@/lang/i18n` 的 `setLanguage` → `hookTools.update(locale)` → 所有 `useI18n` 组件重渲染。
- 勾选状态由 `useSettingValue('common.langId')` 驱动（`useActive`），保证与持久化值一致。

### 4.3 languageChanged 事件监听场景

`state_event.languageChanged`（`src/event/stateEvent.ts` 类型化触发）的监听方用于处理「需要重建页面才能正确刷新文案」的场景：

- `src/screens/Home/Vertical/Main.tsx`（及同目录多页）：`handleHide` 在语言变化时关闭设置页可见性——语言切换后设置页会被卸载重建，确保新语言文案完整生效（该处理对 `themeUpdated` 同样生效，因为主题/语言这类全局变更都可能需要重建部分页面）。

组件内的文案则无需该事件——`useI18n` 的 hookTools 机制已保证自动重渲染。

### 4.4 初始化与 UI 挂载的时序

- `initI18n` 位于初始化管道靠前位置（`initTheme` 之后、`initUserApi` 之前，见 `src/core/init/index.ts`），保证任何 UI 与业务代码接触 `global.i18n` 之前已完成 `createI18n` + `setLanguage`。
- 若因特殊路径在 `createI18n` 之前调用 `useI18n()`，hook 的初始 locale 为 `'en_us'`（`i18n?.locale ?? 'en_us'`），且 `t` 返回 `''`（`i18n?.getMessage(key, val) ?? ''` 空值兜底）——不抛错但文案为空，属于需要避免的边界（见 §9 FAQ）。
- `global.i18n` 在 `src/config/globalData.ts` 未预置（初始为 undefined），因此 core 层直接使用前必须确认初始化已完成。

### 4.5 与 `configUpdated` 的关系

`core/common.setLanguage` 内部先 `updateSetting`（触发 `state_event.configUpdated`）再触发 `languageChanged`，两者先后发出。`Main.tsx` 同时监听了 `configUpdated`（`hideKeys` 命中时也重建页面）与 `languageChanged`：

- 依赖 `useSettingValue('common.langId')` 的组件由 `configUpdated` 驱动更新（如 `Language.tsx` 的勾选态）；
- 依赖 `useI18n` 的组件由 `hookTools.update`（`applyLanguage` 时）驱动更新；
- 需要整体重建的页面同时监听 `languageChanged`。

新增「语言相关的设置项」时注意区分：改设置值走 `configUpdated`，改语言包/运行时走 `languageChanged`。

## 5. 新增语言的完整步骤

1. **命名**：按 `src/lang/Readme.md` 的 locale 列表命名语言包文件，如 `ja_jp.json`（Android 语言代码风格 `ll_cc`，清单含 `zh_cn` / `zh_tw` / `zh_hk` / `en_us` 等全部 38 项，如 `ar_sa`、`pt_br`、`ru_ru` 等）。
2. **翻译**：以 `zh-cn.json` 为底本翻译，**key 集合必须与 zh-cn 完全一致**（`Message` 类型为 `Record<keyof typeof zh_cn, string>` 的联合，缺 key 编译报错）；保留所有 `{占位符}` 原文位置。
3. **注册**：在 `src/lang/index.ts`：
   - `import ja_jp from './ja-jp.json'`
   - 在 `langs` 数组追加 `{ name: '日本語', locale: 'ja_jp', country: 'jp', message: ja_jp }`
   - `langList` / `messages` 由 `langs.forEach` 自动生成，无需手工改动。
4. **生效**：设置页 `Language.tsx` 自动渲染新语言项；用户选中后 `common.langId` 持久化，重启后 `initI18n` 直接命中。设备语言匹配也走同一 `availableLocales` 判断。
5. **验收**：切换新语言后逐页抽查文案与占位符；确认 zh-cn fallback 路径（新语言缺 key 时降级显示中文）。

### 5.1 新增语言的最小改动文件清单

| 文件 | 改动 |
|------|------|
| `src/lang/<locale>.json` | 新建（以 zh-cn 为底本，key 集合一致） |
| `src/lang/index.ts` | import + `langs` 数组追加一项（`name` / `locale` / `country` / `message`） |
| 其它 | 无需改动——`langList` / `messages` / `availableLocales` 均由 `langs` 推导；设置页与设备语言匹配自动生效 |

> 不需要改 `defaultSetting.ts`：`common.langId` 的类型是 `I18n['locale'] \| null`（`src/types/app_setting.d.ts`），随 `availableLocales` 扩展自动放宽，无需预注册默认值。

## 6. 开发辅助：i18n-ally

VS Code 插件 i18n-ally 的配置分两处：

### 6.1 `.vscode/i18n-ally-custom-framework.yml`

自定义框架解析规则（`monopoly: true`，只启用本框架）：

- `languageIds`：javascript / javascriptreact / typescript / typescriptreact。
- `usageMatchRegex`：`[^\w\d]t\(['"`]({key})['"`]` —— 识别 `t('xxx')` 形式的 key 用法（**第一个捕获组必须是 key**），从而在编辑器内联显示翻译、悬停预览、跳转定义。

### 6.2 `.vscode/settings.json`

| 配置 | 值 | 作用 |
|------|-----|------|
| `i18n-ally.localesPaths` | `["src/lang"]` | 语言包目录 |
| `i18n-ally.keystyle` | `nested` | key 风格（本项目 key 实际为扁平带分隔符，编辑器按嵌套显示） |
| `i18n-ally.displayLanguage` / `sourceLanguage` | `zh-cn` | 编辑时以简体中文为源语言 |
| `i18n-ally.translate.engines` | `["google-cn", "google"]` | 自动翻译引擎 |
| `i18n-ally.sortKeys` | `true` | 保存时排序 key |

> 注意：`keystyle: nested` 与实际的扁平 key 风格存在偏差，i18n-ally 的「新建 key」向导可能生成点分嵌套 key，需手工改为 `__` 分隔。

### 6.3 日常工作流建议

1. 在 `zh-cn.json` 中新增 key（按 §2.2 命名约定，可用 i18n-ally 的「Add key」并在三份语言包间同步）。
2. `t('新key')` 写入组件后，i18n-ally 按 `usageMatchRegex` 识别并内联显示翻译。
3. 缺失翻译时编辑器会标记该 key；用 `i18n-ally.translate.engines`（google-cn/google）批量翻译 zh-tw / en-us。
4. 提交前用 `npm run lint` 与 TypeScript 检查兜底（`Message` 联合类型会拦截漏 key 的语言包）。

### 6.4 配置文件的边界

- `usageMatchRegex` 只匹配 `t('key')` 形式（单/双引号均可，含反引号），**不匹配** `global.i18n.t` 或 `t(\`template ${x}\`)` 动态 key 形式——动态 key（如 `t(\`theme_${id}\`)`，见 [theme.md](./theme.md) §2.3）i18n-ally 无法静态识别，属于已知限制。

## 7. S2T（简体转繁体）机制

S2T 与 i18n 是两个独立机制：i18n 负责界面文案的语言切换；S2T 负责**歌词内容**的简繁转换，由设置项 `player.isS2t`（默认 false）控制：

| 维度 | i18n | S2T（player.isS2t） |
|------|------|---------------------|
| 作用对象 | 界面文案（语言包 key） | 歌词文本（lyric/tlyric/rlyric/lxlyric） |
| 开关 | `common.langId`（zh_cn/zh_tw/en_us） | `player.isS2t`（布尔） |
| 实现 | `src/lang/` 运行时 | `src/utils/simplify-chinese-main/` 的 `tranditionalize` |
| 触发时机 | 语言切换 / 初始化 | 歌词获取与桌面歌词渲染时 |

- 转换实现：`src/utils/simplify-chinese-main/`（chinese.js 的 `tranditionalize` 函数，含类型声明 index.d.ts），经 `src/utils/index.ts` 导出为 `langS2T`。
- 应用位置：
  - 歌词获取（`src/core/music/utils.ts`）：`player.isS2t` 开启时对 `lyric/tlyric/rlyric/lxlyric` 四类歌词逐一 `langS2T`。
  - 桌面歌词（`src/core/desktopLyric.ts`）：同样按 `player.isS2t` 转换。
- 与 `zh_tw` 语言包的关系：语言切换不影响歌词内容；两套开关独立。
- 设置迁移：`migrateSetting.ts` 将旧版 `player.isS2t` 对象属性扁平化为点分键。

## 8. 使用规范（贡献者必读）

1. **新增 UI 文案必须走 i18n**：所有面向用户的字符串一律 `useI18n()` 取 key，禁止硬编码中文字符串；错误提示、toast、弹窗文案同理。
2. **key 命名**：沿用 `模块前缀 + _ + 语义` 与 `__` 层级分隔（见 §2.2），先搜 `src/lang/zh-cn.json` 是否已有同义 key，避免重复造词。
3. **占位符**：动态内容用 `{name}` 占位符 + `vals` 参数，禁止字符串拼接（影响 zh_tw/en_us 的语序）。
4. **三个语言包同步改**：新增 key 时必须同时补 zh-cn / zh-tw / en-us（TypeScript 的 `Message` 联合类型会在漏补时编译报错）。
5. **非组件层**：使用 `global.i18n.t(key)`，注意其可能尚未初始化（初始化管道中 `initI18n` 之后才可用）。

### 8.1 新增一条文案的检查清单

- [ ] `zh-cn.json` / `zh-tw.json` / `en-us.json` 三个文件都加了同名 key
- [ ] key 命名符合模块前缀 + 语义（无重复）
- [ ] 动态内容使用 `{占位符}`，没有字符串拼接中文
- [ ] 组件内用 `useI18n()`；非组件用 `global.i18n.t()`
- [ ] 文案包含标点与格式信息时三语言一致（如换行 `\n`）

### 8.2 反模式对照

| ❌ 错误用法 | ✅ 正确用法 |
|------------|-------------|
| `<Text>收藏</Text>` | `<Text>{t('collect')}</Text>` |
| `` `已添加 ${name} 首歌曲` `` | `t('list_add_tip_exists')`（或新增带 `{name}` 占位符的 key） |
| `toast('同步失败')` | `toast(t('sync__error_tip'))` |
| 直接 `global.i18n.getMessage` | 组件内用 `useI18n()`（避免遗漏响应式更新） |
| key 用驼峰/中文（如 `playDetailTitle`） | 小写 + `_` / `__` 分隔（`play_detail_setting_title`） |
| 把翻译结果缓存进 state | 存 key（或非组件处调 `global.i18n.t`），语言切换后由 hook 机制自动重译 |

### 8.3 常见踩坑记录

1. **只改了 zh-cn 就提交**：`Message` 联合类型要求三包 key 一致，CI/本地 tsc 会报 `en_us`/`zh_tw` 缺 key；养成一次改三包的肌肉记忆。
2. **动态 key 不翻译**：`t(\`theme_${id}\`)` 这类模板字符串 i18n-ally 无法识别（§6.4），翻译缺失也不报错，需人工核对动态 key 的取值集合。
3. **占位符被翻译者改写**：`{name}` 被改成中文注释或删掉，运行时替换失效、显示 `{name}` 原文；占位符是协议，不是文案。
4. **在 store/action 里做翻译**：store 层属于非组件逻辑，应存 key 或调用 `global.i18n.t`；若把翻译结果存进 state，语言切换后 state 不会自动重译。

## 9. 待人工核对的疑点与 FAQ

1. **`useI18n` 的初始 locale**：`useState(i18n?.locale ?? 'en_us')` —— 若 hook 在 `createI18n` 之前被调用，初始为 `en_us` 而非 zh-cn；常规路径下 `initI18n` 先于 UI 渲染，理论上不会触发，但边界需留意。
2. **`country` 字段**：`zh_tw` 的 country 为 `'cn'`，仅作语言项展示元数据，无逻辑用途。
3. **`keystyle: nested` 与扁平 key 的偏差**：i18n-ally 的部分辅助功能（自动补全、新建 key）可能与实际 key 风格不完全匹配。
4. **Readme.md 的语言清单是 Android locale 全集**：新增语言时文件名必须精确匹配清单（如 `pt_br` 而非 `pt-BR`），否则与设备语言匹配逻辑不一致。
5. **FAQ：为什么设备是繁体却显示简体？** `initI18n` 只匹配 `availableLocales`（当前 zh_cn/zh_tw/en_us）——若设备 locale（如 `zh_hk`）不在列表中，回退 `en_us`；此时需在设置中手动选 `zh_tw`。
6. **FAQ：为什么缺 key 不报错？** `getMessage` 对缺 key 依次回退 zh-cn → 空字符串，运行时不会抛错；漏 key 只在编译期被 `Message` 联合类型拦截（TS 严格检查场景）。
7. **FAQ：为什么初始化回退是 `en_us` 而不是 zh-cn？** 设备语言与可用语言都不匹配时（如设备为 `fr_fr`）选择 `en_us` 作为国际化默认语言，与「zh_cn 仅作为缺 key 时的 fallback」是两个不同机制。
8. **FAQ：`zh_tw` 与 S2T 的关系？** 无直接关系——`zh_tw` 是官方维护的繁体语言包；`player.isS2t` 是用户自行把简体歌词转繁体的功能，两者可同时开启。
9. **FAQ：能否删除某语言的 key 精简包体？** 可以删值但**不能删 key**：`Message` 类型要求 key 集合与 zh-cn 一致，删除 key 会在编译期报错；值为空字符串时 UI 显示空白。
